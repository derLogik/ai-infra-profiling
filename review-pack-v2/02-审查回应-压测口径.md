## 一、第 5 条：最严重的问题——报告里有一个错数

审查说"不同量化内核、执行方式等变量没有隔离，却给出了较强的因果解释"。
顺着查，发现 README 里这句话是**错的**：

> 原文（§6）：「vLLM 在并发 8 时做到 434 tok/s，是 transformers 静态批 4 的 12 倍。」

**问题**：434 是 vLLM **并发 8**，35.9 是 transformers **批 4**。
并发不同，比出来的是"12 倍"其实混了"并发翻倍带来的收益"。

同并发重算：

| 负载 | 并发 | transformers | vLLM | 倍数 |
|---|---|---|---|---|
| 短 | 1 | 9.8 | 71.1 | 7.26× |
| 短 | 4 | 35.9 | 249.0 | 6.94× |
| 中 | 1 | 10.5 | 68.5 | 6.52× |
| 中 | 4 | 37.5 | 213.3 | 5.69× |

**正确结论是 5.7–7.3 倍**，不是一个 12 倍。
有意思的是：**改小之后反而更好讲**——四个格子落在同一区间，
"跨负载、跨并发都稳定在 6–7 倍"比"某一个是 12 倍"可信得多。

README 已改，并留下修正记录。面试手册的 Q11 需要的也是这组数。

## 二、第 1 条：输入格式确实没统一（本轮修了）

| 侧 | 输入构造 | 位置 |
|---|---|---|
| vLLM / SGLang | `messages: [{role: user, content: prompt}]` → 服务端**套 chat template** | `client_bench.py:74` |
| transformers | `tokenizer([prompt] * bs)` → **裸文本**，不套模板 | 原 `hf_bench.py:59` |

后果有两个：
1. **prompt 长度不同**。模板会多出 system/user 标记（约 10–20 token）。
   短负载 128 token 时，这相当于 10% 以上的偏差。
2. **生成行为不同**。模板模式下模型看到的是对话格式，裸文本看到的是续写。

修法：`hf_bench.py` 新增 `make_inputs()` 和 `--chat-template`（默认**开启**，
与引擎侧对齐），并用 `enable_thinking=False` 与 `client_bench.py:82` 保持一致。
另加 6 项单测（`bench/test_hf_bench_inputs.py`），覆盖批量复制、
一维张量提升、老 tokenizer 不认 `enable_thinking` 时的回退。

**但这项修复只对未来的数据有效。** 已有的 `results/transformers*.json`
是裸文本测的，所以：
- 上面那张 5.7–7.3 倍的表，**目前只能当方向性结论**
- 重跑命令见第四节

## 三、顺带结掉的一个悬案（威胁核心结论的那条）

我自己的调度笔记里留了一条："如果 `max_num_seqs` 也是 2，那'2 路并发'的解释就要改。"
这条如果成立，整个瓶颈分析就塌了。现在结掉：

| 证据 | 内容 |
|---|---|
| 源码 | `v1/core/sched/scheduler.py:108` `self.max_num_running_reqs = self.scheduler_config.max_num_seqs` |
| 生效位置 | 同文件 `:644` `if num_running >= self.max_num_running_reqs:` |
| 实测配置 | `results/vllm.json` 的 `server_args` 里明确是 `--max-num-seqs 8` |

**上限是 8，不是 2。** 序列数这道闸不拦，能同时跑 2 个只能是 KV 块不够
（355 ÷ 136 = 2）。"并发卡在 2 是 KV 导致"站得住。

边界必须说清楚：这是**配置 + 源码**的一致性证据，不是"日志里数出 2 个"。
要拿实测并发，仍需 `--enable-logging-iteration-details` 重跑。

## 四、必须重跑的部分（GPU 时间，约 1.5 小时）

### 重跑 1：transformers 基线（口径修正后）

```powershell
# 先杀掉占用 8000 的服务
wsl.exe -d Ubuntu -- bash -c 'pkill -9 -f vllm; pkill -9 -f sglang; sleep 2'

wsl.exe -d Ubuntu -- bash -c 'export PATH=~/venvs/qwen3-infer/bin:/usr/lib/wsl/lib:/usr/bin:/bin; \
  ~/venvs/qwen3-infer/bin/python \
  /mnt/c/Users/USER/work/ai-infra-profiling/bench/hf_bench.py \
  --model-path ~/models/Qwen3-8B-AWQ \
  --batch-sizes 1,2,4,8 --repeats 3 --out ~/work/transformers_v2.json'
```

改动要点：
- `--chat-template` 默认开，与引擎侧对齐
- `--batch-sizes` 加了 2 和 8，**这样每个并发都能和 vLLM 同并发比**
- 结果里新增 `bench_config`，以后再也不会出现"不知道用什么配置测的"

### 重跑 2：对照实验（能支持或否定原假设）

原假设 H：**8 并发下并发只到 2，是因为 KV 块装不下第三个整份请求。**

| 组 | 参数 | 若 H 成立 | 若 H 被否定 |
|---|---|---|---|
| A | 基线 | 并发 2，63 tok/s | — |
| B | `--no-scheduler-reserve-full-isl` | **无变化**（chunk 仍是整个 prompt，128 块 > 83 空闲块） | 有变化说明不是块数约束 |
| C | B + `--max-num-batched-tokens 512` | 并发升到 3–4，吞吐升，TTFT 尾延迟变差 | 并发仍 2 且日志 `num_preemptions` 上升 → H 错 |

**C 组是真正的判据**：只有把单个请求的块需求降到能塞进 83 个空闲块，
并发才可能上升。如果缩了 chunk 并发还是 2，那约束就不在块数上。

三组都要加 `--iteration-details`，否则拿不到实测并发：

```powershell
# 三组各一条命令，--tag 区分，结果不会互相覆盖
python bench/run_matrix.py --model-path <模型> --backends vllm \
  --workloads long --concurrency 8 --iteration-details --tag A
# B 加 --server-arg=--no-scheduler-reserve-full-isl
# C 再加 --server-arg=--max-num-batched-tokens --server-arg=512
```

跑完：

```powershell
python bench/compare_experiments.py preds.json results/vllm__A.json results/vllm__B.json results/vllm__C.json
```
