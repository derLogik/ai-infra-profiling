## 一、显存账本的直接证据

```
L48  INFO [gpu_worker.py:625] Available KV cache memory: 0.78 GiB
L50  INFO [kv_cache_utils.py:2032] GPU KV cache size: 5,696 tokens,
     Maximum concurrency for 4,096 tokens per request: 1.39x
```

**这两行是整个报告的地基。**

- KV 池 = 0.78 GiB，这是**显示舍入**：`801 MiB ÷ 1,024 = 0.7822 GiB`
  → 报告里的 801 MiB 与日志的 0.78 GiB 是同一个数
  （若按 798 MiB 算只有 `798 ÷ 2.25 = 354` 块 → 5,664 token，与日志的 5,696
  对不上；所以取 801 MiB，`801 ÷ 2.25 = 356` 块 → 5,696 token，吻合）
- `5,696 tokens` 与 `356 × 16 = 5,696` 完全吻合 → **块数是 356**
- `801 MiB ÷ 2.25 MiB/块 = 356` 块，与上一行自洽
- `1.39x` = `5,696 ÷ 4,096` → 正好是"池子只有 1.39 倍上下文长度"
- 这几个数与报告 §2 的推导链互为验证，不是同一处算两遍

## 二、并发上限不是序列数导致（排除替代解释）

| 证据 | 内容 |
|---|---|
| 源码 | `v1/core/sched/scheduler.py:108` `max_num_running_reqs = max_num_seqs` |
| 生效处 | 同文件 `:644` `if num_running >= self.max_num_running_reqs:` |
| 实测参数 | `results/vllm.json` → `--max-num-seqs 8` |

上限是 8。8 个请求同时到达时，这道闸不拦，所以"同时只跑 2 个"
只能由 KV 块数解释（355 ÷ 136 = 2）。

## 三、前缀缓存 A/B（单变量）

同一份权重、同一台机器、同一组负载，唯一差别是 `--enable-prefix-caching`：

| 负载 c8 | 无缓存 | 有缓存 | 倍数 | TTFT |
|---|---|---|---|---|
| 长 2048→128 | 63.4 | 380.8 | 6.01× | 8.089 → 0.104 s |
| 中 512→256 | 276.9 | 504.3 | 1.82× | 1.585 → 0.076 s |
| 短 128→128 | 434.4 | 552.3 | 1.27× | 0.555 → 0.066 s |

**必须同时说清的限定**：这组 A/B 里 8 个请求**共用同一个 prompt**，
缓存命中率接近 100%，所以 6.01× 是**上限**，不是通用收益。
prompt 越长收益越大这一规律仍然成立，且指向 prefill 是主导成本。

## 五、两个引擎的公平对比

vLLM / SGLang 双方都：`awq_marlin`、前缀缓存关闭、CUDA graph 开启、`max-running-requests 8`。

唯一差异是显存占比：vLLM `0.85`、SGLang `0.88`（SGLang 长 prompt 需要更高
占比才能不返回 400）。**SGLang 拿了更高的占比却只有更小的 KV 池**
（2,554 vs 5,696），这使"差在 KV 容量"的结论更强而不是更弱。

| 负载 c8 | SGLang | vLLM | 倍数 |
|---|---|---|---|
| 短 | 436.5 | 434.4 | 1.00× |
| 中 | 156.2 | 276.9 | 1.77× |
| 长 | 42.6 | 63.4 | 1.49× |
